# 陕铺客户交付完整落地方案

日期：2026-11-03。实施规格：`../specs/2026-11-03-customer-release-closure.md`。基线：main `92d83bddcc14a43f7f8183a0a3d1260238c0c45c`。

本文是原《v1.0 客户交付版》的执行收口补充：复用已实现能力，处理新增证据确认的阻塞，替代“代码完成即交付”的口径。本文中的改动、工具及门禁均为待执行计划；本轮仅形成方案，不表示已修复或部署。

## 1. 交付路线与固定决策

1. 一套项目、同一套生产数据，先以 catalog 模式交付受控的商品后台，再切 commerce 开放小程序交易。
2. 沿用仓库现有 Docker Compose：Nginx、Vue 后台静态服务、Spring Boot、MySQL、Redis；staging 与 production 分开部署和存储，严禁共用数据库、Redis 或素材写目录。
3. 初期保留已实现的 mounted 素材存储，配合异机备份；不为本轮强制引入新对象存储。更换为 COS/S3 时单独实现存储适配、访问 URL 及数据迁移，不直接声称已有该能力。
4. 默认同一 HTTPS 域名服务后台、API 和素材，复用现有代理结构；如后台需独立域名，增加精确 server_name、CORS 与发布配置，不使用通配来源。
5. 构建固定版本镜像，在 staging 验证后按相同摘要部署 production。客户服务器不从 main 随时拉取并重建。
6. 不迁移框架或大幅升级技术栈。先锁定当前实际能通过测试的 Java、Node、pnpm 与基础镜像版本；依赖漏洞按实际扫描结果做必要升级和复测。

建议小规模试运营先按 4 核/8GB、足够 SSD 容量准备单机部署评估，数据库和文件放持久卷，另外准备异机备份目的地。该规格只是初始估算，正式容量以商品图片总量、预计并发和压测结果为准；高可用及多机扩容不属于默认交付承诺。服务器可先在客户现有云账号内选用，避免新增一套供应商与账号。

## 2. 范围冻结：第一天就确认

### 默认 v1.0 范围

实物商品商城、商品/内容/SKU/库存运营、基础优惠券/满减/包邮、地址、购物车、微信支付、整单单包裹发货、物流查询、整单售后退款、对账、权限审计、反馈与评价、备份监控、操作培训。

### 必须确认的差异

| 待确认事项 | 本方案默认 | 如果客户要求不同 |
|---|---|---|
| 是否含分销/二级分佣 | 不含，现有 Issue #48 不自动进入范围 | 另立结算、提现、权限与验收规格 |
| 是否含会员价/付费会员 | 不含 | 重新评估营销金额和权益链路 |
| 是否卖课程等虚拟商品 | 本次仅开放实物商品 | 补虚拟履约、交付凭证和售后规则后才开放该类型 |
| 运费 | 基础运费与免邮门槛 | 若有偏远地区/不配送地区，必须形成可执行限制，不只是公告文字 |
| 退货退款 | 整单，按已有状态流程验收 | 部分退款、拆包、换货另定义 |
| 店铺名称修改 | 客户可修改页面展示名 | 微信平台账号名仍由有权限的负责人处理 |
| 上线支持 | 建议上线后 14 天缺陷保障 | 明确值班时段、联系渠道及新增需求边界 |

签字确认的是功能范围和验收口径，不把所有旧 GitHub Issue 都视作承诺。已有功能重叠的 Issue 按复验结果整理，旧 PR 不直接合并。

## 6. M1：让客户开始录商品

### 部署步骤

1. 固定 release 候选 commit 与镜像摘要；准备 staging 的独立密钥、数据库、Redis、素材和日志目录。
2. 新库仅执行审核后的正式 schema/字典；旧库先备份、在副本升级验证，再按同版迁移执行。首次引导和后续升级使用不同入口，避免重复 init。
3. 在服务未对外开放时创建超级管理员、替换默认密码，再建立商品运营账号；生产应用账号不使用数据库 root。
4. 应用 catalog 模式，启动 MySQL/Redis，再完成迁移及检查，再启动后端/后台/Nginx；外层限制受控访问，DB/Redis/8085 不暴露公网。
5. 后端内部就绪、后台登录、图片上传、商品保存、Excel 导入均通过后再开放客户入口。
6. 在 production 重复使用已验证镜像和迁移，执行 M1 清单，客户开始正式录入。今后升级保留该数据库和素材目录。

### M1 验收清单

- [ ] 正确域名 HTTPS 可访问，证书有效；服务器重启服务可恢复。
- [ ] 商品运营账号可登录、改密码；无财务/角色管理权限；API 越权被拒绝。
- [ ] JPG/PNG 及实际支持的 WebP 上传与展示通过；不支持格式提示明确；不要求人工复制临时链接。
- [ ] 一件单规格、一件多规格商品保存成功，金额单位和库存正确，默认下架。
- [ ] 修改名称、图片、规格、价格、库存时校验可理解，库存调整有原因和流水。
- [ ] Excel 预检不写库；正式导入成功；错误行可定位；更新完整 SKU 集合规则明确。
- [ ] 预览、保存、刷新、重新登录一致；客户不会把草稿误认为已发布。
- [ ] 商品与图片在容器重建后保留；新机恢复备份后仍能展示。
- [ ] 公众所有 app-api 入口、模拟支付和交易任务关闭，测试直接请求也不能调用。
- [ ] 客户照教程独立录入至少一件真实商品并签收 M1。

M1 的签收只代表商品后台可使用，不写“商城已上线”。

## 7. M2：完整真实交易与运营收口

### 必须复验的业务矩阵

| 范围 | 成功路径 | 必测异常/边界 |
|---|---|---|
| 登录 | 真微信 code 登录、刷新、退出；保留手机号登录则实测 | Token 过期、用户拒绝授权、协议未同意、账号注销后的状态 |
| 商品 | 列表/分类/搜索/详情与后台一致；SKU 图价库存一致 | 下架、删除/禁用分类、缺图、无库存、规格未选、失效跳转 |
| 价格营销 | 商品价、优惠券、满减、运费和实付一致 | 重复领券、失效券、边界金额、优惠叠加、前端篡改价格 |
| 库存 | 下单扣减，取消/超时按规则释放，退款按规则处理 | 最后一件并发下单、重复请求、编辑/导入/回退与交易并发；库存不得负数或重复回补 |
| 下单 | 立即购买与购物车隔离，地址与金额快照固定 | 连点提交、网络超时重试、跨用户查看/取消/退款、订单中商品后续改价 |
| 支付 | 实单支付、异步通知、主动查单、关单 | 重复/乱序/伪造通知、金额与商户/AppID 不匹配、超时取消与支付竞争、已支付重复预付 |
| 发货物流 | 后台填写真实单号，小程序显示真实轨迹 | 错单号、重复发货、物流超时、无轨迹、平台发货录入失败；不可返回假轨迹冒充真实结果 |
| 售后退款 | 仅退款、退货退款收货、拒绝、撤销、实单到账 | 重复审核、退款处理中/失败、重复通知、重启后任务恢复、订单/支付/退款/库存一致 |
| 对账 | 本地订单与渠道账单逐笔核对，差异可处理 | 未通知支付、漏退款、本地/渠道金额不一致、重复处理、跨日边界 |
| 用户服务 | 反馈在后台显示，收货后可评价，带图评论 | 追踪 #56/#57/#58；图片上传与权限、隐私拒绝、客服入口不应空跳 |
| 权限审计 | 商品/客服/售后/财务/只读按矩阵隔离 | 不能靠隐藏按钮；Token 失效、账号停用、审计业务失败记录也正确 |

库存并发、回调幂等及权限使用实际 HTTP→过滤链→服务→数据库验证。金额全程以分核对；客户端显示元。每个实单记录订单号、支付交易号、退款号、时间、证据及测试清理方式，不随意删除资金流水。

### 微信渠道必须核对

- AppID、商户关联关系、经营主体和账号权限真实可用；截图中的备案状态不能代替当前后台结果。
- 商户实际使用平台证书还是微信支付公钥验签。当前 `WechatPayService` 仅按单个平台证书序列号验签；按账号实际模式支持对应密钥，并补轮换/有效期预警和过渡期验证。若采用官方 SDK，限定改动并完整回归，不同时重写订单状态机。
- 退款回调必须无需本系统用户 Token 即可到达验签逻辑；通知应答、重试、幂等和主动查询按微信文档验证。
- 快递 100 只解决物流轨迹查询，不能替代微信平台发货信息管理。核对该账号适用的发货/确认收货/结算要求；需要时接入 API、失败重试和同步记录，或在初期明确人工平台录入流程、负责人、逐单核对台账。客户若要求后台一次发货即自动同步，自动接入必须完成后才能签收该能力。
- staging 回调与 production 回调、AppID、订单标识不混用；真实小额验收订单经客户财务同意安排，留存账单证据。

官方参考（实施时再核对当前文档）：[退款结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4012791906)、[小程序交易资金管控说明](https://pay.wechatpay.cn/doc/v3/institution/4019778929)。是否适用以客户账号与微信后台要求为准，不将合作伙伴特定场景说明直接视为所有商户的统一要求。

### 真机与提审

体验版使用最终域名配置，iOS/Android 各至少一台实际微信测试：登录、浏览、选规格、加购、地址、下单、支付返回、订单刷新、物流、售后、图片评价、反馈、分享、隐私授权、客服。检查弱网、切后台再进入、Token 过期及重复操作。

按真实数据收集行为配置隐私指引、用户协议、售后政策及权限说明，经营资质与商品类别由客户确认。若虚拟商品暂不交付，限制其新增/上架或明确隐藏入口。截图第 4 张的“相关前置许可”不能据此一律选择是/否，应按实际业务资料核对。

## 8. CI、构建与发布必须补齐

### 每次合并的快速门禁

固定 Java/Node/pnpm；后端单元及必要集成测试；后台 typecheck/build；小程序 API/生产配置契约；secret scan；权限规则；数据库空库迁移、旧库升级、重复迁移；交付文档命令一致性。所有外部命令失败立即终止，输出测试报告并上传 artifact。

### 候选版本的完整门禁

在隔离测试库、Redis、后端及浏览器环境中运行现有 `verify-trade-flow.ps1`、`verify-commerce-consistency.ps1`，补齐实际权限、并发、回调过滤链及回退库存测试。Mock 交易脚本只能作为隔离环境测试，不能把 Mock 开关打开到 production。在线依赖审计单独归档，网络失败写“未完成”，不能当通过。

现有 `.github/workflows/v1-delivery.yml` 尚不等于完整发布流水线；补 Redis/后端/端到端任务、失败注入和证据输出，并核验 pnpm 安装与缓存初始化顺序。真实微信验收与 HBuilderX 构建安排在具备权限的受控机器，产物绑定 commit、环境和版本，不能复用不明来源 dist。

### 可重复发布

拟新增 release 工具（当前不存在，执行时实现）：

- 预检：读取不含明文回显的环境配置，核对模式、证书、卷权限、域名、空间、备份和迁移状态。
- 迁移：等待 MySQL 健康，备份成功后执行发布清单，全部成功才启动新应用。
- 发布：拉取固定镜像摘要，更新后端与后台，等待实际就绪，运行只读冒烟，再切入用户访问。
- 记录：release manifest 包含 commit、镜像摘要、工具链版本、迁移校验、配置版本、执行人、时间和报告。

Linux 云主机上使用经过测试的 shell/Compose 发布入口；现有 PowerShell 迁移/检查脚本可在受控部署机通过安全连接调用，或明确安装固定版本 pwsh。两种方式只选定一种正式操作路径写进手册，不能让现场人员自行拼接。

## 9. 备份、监控与故障恢复

### 备份与恢复目标

建议小规模试运营暂定 RPO≤1 小时、RTO≤4 小时，需由客户接受并通过数据量演练证明。RPO 表示最多可接受丢失多久数据，RTO 表示故障后恢复多久。不能只写指标而没有定时任务和异机副本。

- 每小时数据库一致性备份及素材增量快照，成套标记时间和清单，完成后加密上传到独立故障域；备份失败/超过 1 小时无有效备份触发告警。
- 文件写入与数据库记录的时间差需纳入备份策略，恢复后跑图片引用完整性检查；必要时短暂停写形成一致检查点。
- 保留最近 48 小时小时级、30 天日级备份；保留周期按客户数据要求调整，考虑订单/隐私数据，限制下载权限。
- 每月在隔离环境抽查恢复；首次交付前必须实际恢复数据库和图片，不仅检查压缩包存在。
- Redis 明确作为缓存/会话使用还是含不可丢任务状态，盘点后制定备份或重建策略；恢复期间使旧会话失效并重新登录。

### 最低监控

外部 HTTPS、后端就绪、DB/Redis、CPU/内存/磁盘、证书/验签材料有效期、图片上传错误、支付和退款失败、待处理任务、平台发货同步失败、备份新鲜度。后台告警页之外必须有负责人能收到的通知渠道；渠道和接收人由客户确认，交付前发一次测试告警确认收到。

日志保留请求追踪号和业务单号；不记录明文密钥、完整身份证明或不必要的收货隐私。控制日志轮转和磁盘上限，避免日志占满影响数据库。

### 回滚原则

保留上一个已验证镜像摘要及配置。数据库采用兼容性增量变更：先加后用、延后删除，确保旧镜像能读取。应用问题优先回滚应用并保留所有新订单；不直接恢复老数据库覆盖上线后交易。

若数据库损坏，先停写和入口、保留故障库，在隔离环境恢复；结合微信渠道账单核对备份时间点之后的支付/退款再恢复服务。退款、支付状态不确定时禁止盲目重复出款。客户负责人和财务参与确认。

### 发布中

1. 冻结后台写操作，保存数据库与素材检查点，确认异机备份完成。
2. 按 release manifest 执行迁移，失败停止；不修改迁移历史强行越过。
3. 发布固定镜像，等待业务就绪；管理员登录和商品只读检查通过。
4. catalog→commerce 切换前，确认渠道和小程序版本已就绪；先少量体验用户完成真实交易。
5. 核对订单、支付、退款、库存、发货同步及对账，确认无未解释差异后开放正式入口。

### 发布后

观察至少 48 小时并覆盖一次日终对账、一次备份；明确每天查待发货/退款异常/对账差异的客户岗位。失败回滚按上节操作；记录所有已产生的真实资金单据。
