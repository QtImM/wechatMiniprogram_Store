# 客户交付最后冲刺计划

> 2026-11-27 建立。以 [v1.0 客户交付版总计划](v1.0%20客户交付版.md) 和 [最终验收报告](../../delivery/v1.0-final-acceptance-report.md) 为验收依据。目标是 M2 真实商城交易交付；M1 商品录入只能作为有范围声明的阶段性交付。

## 0. 当前基线与放行原则

- 本机 `dev + commerce` 使用模拟微信身份、退款和物流，只能开发调试；所有本地截图均不计作真实渠道验收。
- 2026-11-25 曾在客户腾讯云服务器完成 `catalog` 预演，五个容器和健康探针当时通过；今天从本机访问 `https://bhtjl.top/`、`/healthz`、`/readyz` 均超时。先核实域名、443、反向代理及服务器现状，不推断客户服务仍正常，也不直接覆盖现有部署。
- 当前工作区有未提交的登录配置、HBuilderX 本地 API 地址和交付模式预检修正；这些改动先复核、测试并合入固定提交，再生成交付产物。
- 缺少客户 AppSecret、手机号隐私声明、支付公钥 ID、真实物流账号、异机备份与告警信息的实际核验。没有真实联验证据，不放行 M2。
- 每一关保留命令输出、脱敏配置、截图、业务单号和镜像哈希。失败即停在当前关；修复后重跑受影响的关，不靠口头确认放行。

## 1. D0：冻结范围并恢复线上可达

**技术方**

- [ ] 固定候选 commit，审查当前未提交改动，跑完后端、后台、小程序编译、数据库迁移、交付工具和 CI 门禁；保留失败项与修复记录。
- [ ] 只读盘点客户服务器：DNS、443/TLS、宝塔/Nginx、现有网站和端口、五容器、日志、磁盘、数据库迁移历史与备份状态；定位 `bhtjl.top` 当前超时原因。
- [ ] 恢复 `https://bhtjl.top/healthz`、`/readyz` 和后台登录的外网访问，核对证书覆盖域名与到期日；确认是客户部署而非本地旧容器。
- [ ] 列出客户现有资料与缺项，只记录是否可用，不把密钥写入仓库、聊天或验收文档。

**放行证据**：固定 commit、CI 结果、域名与证书检查、容器和 HTTP 健康响应、服务器现状清单。线上不可达时停止发布和二维码分发。

## 2. D1：M1 正式商品录入交付门槛

**技术方**

- [ ] 用受控 `.env.prod` 执行预检：`prod + catalog`、Mock 关闭、支付关闭、独立强密码、明确 HTTPS 域名和 CORS；使用固定镜像包而非现场临时构建结果。
- [ ] 对正式库做备份和迁移校验，核对版本、校验和、核心表与图片目录；验证数据库和素材的容器重建持久化。
- [ ] 使用客户独立后台账号完成登录、改初始密码、角色限制、商品与 SKU、图片、库存、运费、导入导出、上下架的实际操作。
- [ ] 验证全部 `/app-api/` 和交易后台入口在 `catalog` 返回 503；执行加密异机备份、隔离恢复、告警送达和应用回滚演练。

**客户方**：提供受控服务器/域名访问、运营人员账号、真实商品图片与价格库存、配送和售后政策、异机备份存储与告警接收人；独立操作并确认录入流程。

**放行证据**：最终验收报告 C-01 至 C-07、备份恢复与回滚报告、客户操作截图。M1 可先签收后台录入，签收文件须明确小程序和交易未开放。

## 3. D2–D3：staging 真实渠道与全链路验收

**客户方先补齐并核验**：小程序 AppID 归属与有效 AppSecret、开发/体验成员权限、手机号隐私保护指引、request/upload/download 合法域名、商户绑定和支付开通、支付公钥及对应 ID、快递 100 正式账号、可实际查询的物流单号、iOS/Android 真机与小额实单验收授权。

**技术方**

- [ ] 建立与正式环境分离的 staging 数据库、Redis、素材目录和 HTTPS API，运行 `staging + commerce`；核对微信登录、交易、退款、物流均非 Mock。
- [ ] 用客户 AppID 构建 staging 体验版并上传，取得二维码；真机验证隐私声明、手机号授权、微信 code 换 OpenID、同一用户再次登录、Token 刷新和退出。
- [ ] 按完整真机用例回归首页、分类、搜索、详情、购物车、优惠、运费、地址、订单、支付、售后、评价和异常路径；覆盖 iOS、Android、授权拒绝与网络失败。
- [ ] 在授权的小额实单上核对微信支付、异步回调、主动查单、退款、退款回调/同步、对账与异常工作台；用真实快递单核对轨迹和发货流程。
- [ ] 对每个失败项修复后用同一候选版本重建镜像和小程序，再重跑受影响链路及 CI。

**放行证据**：体验版二维码、两端真机截图、真实微信交易/退款号、回调与对账记录、物流查询结果、完整用例表。Mock 成功、模拟器成功或只有后端单测均不能替代此关。

## 4. D4：M2 正式发布与客户签收

- [ ] 锁定通过 staging 的 commit、镜像 ID/SHA256、数据库迁移清单和小程序版本；备份正式库和素材，确认可恢复及回滚窗口。
- [ ] 正式环境切 `prod + commerce`：真实微信登录/支付/退款/物流，Mock 全关，HTTPS 与合法域名匹配；发布同一组受验镜像。
- [ ] 构建 production 小程序，检查包内 API 域名及无本地地址；上传、提交微信审核，审核通过后发布。未获微信审核通过不得宣称小程序已上线。
- [ ] 正式环境进行授权的小额支付、退款、发货、物流、售后、对账和后台角色冒烟；核对健康、日志、告警、备份定时任务与恢复点。
- [ ] 填写最终验收报告中的地址、AppID、commit、镜像哈希、全部业务证据和已知限制；客户指定验收人按 M2 范围签字，交接账号、备份密钥保管与运维联系人。

**放行标准**：最终验收报告的 M2 真实渠道项都有可追溯证据，微信审核与正式发布完成，客户能独立完成核心操作，备份恢复/回滚与告警均已实测。任一项缺失则保持 M1 或 staging 状态，不标记完整交付。

## 责任与节奏

| 工作 | 主责 | 启动条件 |
|---|---|---|
| 代码收口、CI、镜像、部署、联调、证据归档 | 技术方 | 立即开始 |
| 服务器和微信/支付/物流权限、隐私声明、经营资料 | 客户方指定持有人 | D0 并行提供 |
| 真机、资金与最终验收确认 | 技术方执行，客户方授权和签收 | D2 真实渠道可用后 |

D0–D4 是依赖顺序，不是无条件的日历承诺。每天只更新“通过的门槛、证据链接、阻塞责任人和下一步”；客户资料或平台审核未到位时，技术方继续完成不依赖它们的工作，整体交付日期随实际解阻时间调整。
