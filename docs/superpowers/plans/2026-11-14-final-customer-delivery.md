固定路线：**修复并整合候选版 → M0 技术验收 → M1 正式商品录入后台 → M2 真实商城 → 培训与签收。**

这样先解决 Liming 要客户尽快录商品的需求，支付、备案和小程序发布按独立依赖推进。M1 和 M2 使用同一生产数据；staging 使用独立测试库、Redis 和素材目录。

## 2. 范围和权限先按以下默认执行

默认实物单商户商城：商品分类/素材/SKU/库存、内容运营、现有基础优惠券/满减/包邮、地址购物车、微信支付、单包裹发货、物流、整单售后退款、评价反馈、财务对账、权限审计与备份运维。

分销、会员付费、虚拟课程、拆包、部分退款、多仓、ERP 等先对照合同。发现原合同已承诺的内容，补入任务、验收与工期；新增需求另行确认。配送范围、偏远地区限制、退货规则必须在系统行为和客户政策之间一致。

账号默认分工：客户商品运营使用商品/素材权限，内容运营按需增加内容权限；财务、客服和售后使用对应角色；只读不能写入。超级管理员单独保管。店铺展示设置当前要求超级管理员，教程必须说明；需要委派运营时单独调整最小权限，不能直接共享超级管理员账号。

## 6. M1：部署客户可正式使用的录入后台

### 环境与数据

- staging 和 production 使用不同 Compose 项目名、目录、数据库、Redis 与素材写路径。即便共用主机，也不得共用数据目录；共用主机不算灾备。
- 全新客户：使用清洁初始化工具，生成独立随机数据库/Redis/管理员密码，无演示会员、商品、订单或异常记录。
- 已有客户数据：先完整备份，在副本比较迁移校验与数据来源。历史品牌 SQL 校验差异逐项核对，不删除迁移记录、不重置数据库、不全表清理演示数据。
- M1 生产数据在转 M2 时原地保留，不通过覆盖测试库或重新导入 demo 完成切换。

### 部署与验证

先在 staging 验证封存包，再在生产导入同一包，核对 commit、包校验和及镜像 ID；设置真实 HTTPS、素材目录属主、私钥权限、独立数据库账号和受控管理入口。MySQL、Redis 和后端端口不得直接暴露公网。

启用 catalog 模式，检查网关与后端实际拒绝交易访问；无账户可绕过权限。客户使用个人账号，能改商品资料但不能操作资金或系统配置。店名与 Logo 修改权限单独说明。

M1 签收操作至少包括：登录并修改初始密码、上传图片、新建单规格及多规格商品、调整库存并写原因、下载模板/导入预检/修正错误/确认、改名称与图片、查看预览、重登及容器重建后核对、误操作处理。由客户亲自操作，技术方记录问题和结果。

M1 交付资料：正式 HTTPS 地址、个人账号及单独交接的初始密码、岗位权限表、图文教程、备份与恢复结果、待开放功能说明、录入阶段验收记录。初始密码修改后清理不再需要的引导配置。

## 7. 备份、恢复、监控和回滚必须实际落地

### 备份和恢复

- 数据库与素材形成一致检查点；备份包带文件清单和校验和，加密后复制到经确认的独立故障域存储。仅“是挂载目录”不能证明异机，需要核对目的存储和故障域。
- 首次交付前恢复到新隔离库和新素材目录；逐表核对商品、SKU、库存流水、订单、支付退款、迁移与图片引用，核对图片哈希并重新启动应用读取。
- 备份过程中停写窗口必须可控；发布从冻结写入到完成迁移和验证应保持同一维护窗口，不能备份后恢复业务写入、再拿过时检查点做升级保证。
- 升级前的备份要校验、加密并确认独立副本成功，再进行数据库变更。失败停止，不覆盖线上数据。
- 暂以 RPO≤1 小时、RTO≤4 小时为待客户接受的目标。现有小时任务和 90 分钟过期判断不能直接证明该目标；按数据量改为例如 30 分钟备份、60 分钟内有效性监控，并实测耗时和可恢复点，达不到则调整方案及承诺。
- 保留策略落实到自动任务或存储生命周期：建议保留最近 48 小时恢复点和最近 30 天每日副本；执行删除前检查有效独立副本，提供预览和记录，不能只写文档或删除最后可用备份。
- 每月安排隔离恢复抽检，指定运维负责人；密码与备份分开保管。

### 监控

覆盖外部 HTTPS、后端就绪、DB/Redis、磁盘、CPU/内存、证书与验签材料有效期、上传失败、支付退款异常、对账差异、备份失败/过期。监控在业务主机故障时仍应能发现问题。日志轮转、通知去重与恢复通知一并配置。

客户指定接收人并授权渠道后，实际发送一次测试通知，确认收到；未送达不能勾选告警通过。通知不得包含密钥、完整收货信息或备份密码。

### 回滚

保留上一已验证镜像包与配置，审查数据库兼容性后演练应用回滚，验证新产生的业务数据仍在。当前工具未完成自动应用回滚闭环，需补可重复入口、失败处置和记录。

若数据库损坏，先停止写入并保留故障库，在隔离环境恢复，再核对备份后真实支付退款。禁止直接恢复旧数据库覆盖新增订单，禁止对状态不确定的资金重复出款。

## 8. M2：真实商城、真机和平台发布

### 资料和配置

客户持有人提供协作权限及必要确认：实际 AppID/Secret、微信商户关联、支付私钥/API v3 Key、实际验签模式、退款回调、物流账号、常用承运商、客服/退货地址、配送与售后政策。密钥通过安全通道进入部署环境，不写 Git、教程、群消息或截图。

由技术方在实际账号中核对名称、备案、服务类目、隐私指引、服务器域名、回调和发货信息管理/结算要求。此处列为待核验事项，不预先猜测账号是否适用。需要自动发货同步时补 API、重试和流水；若初期明确人工平台录入，必须有客户接受的逐单流程、责任人和核对记录。

### 真实验收矩阵

1. 登录授权：首次、重复、取消、失败、隐私拒绝及会话过期。
2. 商品/地址/购物车：搜索、规格价格、库存不足、上下架同步、配送范围和运费。
3. 下单支付：成功、取消、返回失败后查单、重复请求、重复/伪造回调、跨用户订单访问。
4. 履约：真实发货、真实物流查询、必要的平台发货记录、收货及超时任务。
5. 售后：仅退款、退货退款、拒绝/撤销、处理中/失败恢复、重复通知和重复审核。
6. 对账：订单/支付/退款/渠道账单逐笔核对；金额以分核对，库存流水与销量一致。异常必须解释并关闭。
7. 用户服务：收货后评价、图片评价、反馈后台可见、客服入口。
8. iOS/Android 微信真机：弱网、切后台、重新进入、分享、隐私和支付返回；预览页不能替代真机。

实单金额和人员由客户财务确认；技术方完成操作指导、业务追踪与核对。记录订单、交易、退款及物流单号和时间；这些作为受控验收附件，不公开进代码仓库。

### 构建与发布

有权限持有人完成 HBuilderX 必需登录/扫码后，技术方以最终 API 域名和生产配置重新发行编译、检查产物、上传体验版并测试。构建输出绑定 commit、配置、版本和校验值；不复用开发目录旧产物。

平台允许发布、真实链路通过、客户确认窗口后，完成冻结写入、有效独立备份、迁移与镜像导入、服务就绪、commerce 配置预检、小程序正式版本发布和小额冒烟，按预先约定的先后顺序开放入口；避免用户端与后端版本错配。

上线观察至少 48 小时并覆盖日终对账和自动备份。异常达到资金/权限/数据阻断标准时停止开放并按演练路径恢复；不能把观察期静默当作没有异常的证据。
